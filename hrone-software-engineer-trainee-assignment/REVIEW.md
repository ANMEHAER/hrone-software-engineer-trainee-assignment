# REVIEW.md

This review compares the starter implementation with `openapi.yaml`, `DATA_MODEL.md`, and the stated attendance rules. The fixes below are reflected in the updated `app/main.py`.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health()` | It returns `{"status": "ok"}` even when MongoDB is unavailable, so readiness can report a healthy app that cannot serve requests. | Stop MongoDB and call `GET /health`; the starter still returns 200. | Ping MongoDB and return HTTP 503 if the ping fails. |
| 2 | Startup / index setup | The starter does not create required indexes. Duplicate employee codes and duplicate attendance records can occur under concurrent requests. | Inspect indexes on a fresh database; send simultaneous requests for the same employee or employee/date. | Create indexes at startup, including unique indexes for `employees.emp_code` and `(attendance_logs.emp_code, attendance_logs.date)`. Catch duplicate-key errors and return 409. |
| 3 | `EmployeeIn` | The starter accepts malformed employee codes, emails, dates, and shift times because these fields are plain strings. | Send an invalid code, malformed email, `joined_on="2026-02-30"`, or `shift_start="25:70"`; these should return 422. | Add Pydantic validation for employee code, email, date, and `HH:MM` shift formats, and reject identical shift start/end times. |
| 4 | `create_employee()` | Checking for an existing employee before insert is vulnerable to a race between concurrent requests. The creation timestamp is also naive, and the starter does not return it in the required epoch-millisecond format. | Send parallel POST requests with the same `emp_code`, or inspect the stored `created_at`. | Use a unique index to handle races, catch `DuplicateKeyError`, and store the creation time in UTC. |
| 5 | `create_employee()` response | MongoDB's internal `_id` should not be exposed as an API identifier; the contract uses `emp_code` as the employee identity. | Create an employee and inspect the response for an unexpected `id` or `_id`. | Remove `_id` from the response and serialize supported values. |
| 6 | `list_employees()` pagination | The starter calculates `skip = page * page_size`, which skips the first page's records. | With page size 2, request page 1; the first two employees are missing. | Calculate skip as `(page - 1) * page_size`. |
| 7 | `list_employees()` total and ordering | `total` counts every employee instead of only employees matching the department filter, and results have no stable sort order. | Filter by a department with fewer employees than the full collection and compare `total`; repeat requests and inspect ordering. | Count using the same filter and sort by `emp_code` before pagination. |
| 8 | `list_employees()` input checks | Invalid page values and oversized page sizes are not rejected. | Try `page=0`, `page_size=0`, or `page_size=101`. | Validate that `page >= 1` and `1 <= page_size <= 100`. |
| 9 | `compute_late_minutes()` | It builds shift start on the punch-in's calendar date, so overnight shifts are handled incorrectly. It also checks the floored minute count against 10, which misses a punch-in 10 minutes and 1 second late even though the rule says any delay strictly over 10 minutes is late. It depends on naive/local datetime behavior too. | For a `22:00–06:00` shift, test a punch-in at 05:00 IST; shift start should be the previous evening. | Convert instants consistently and calculate the actual shift start date, including overnight shifts. Keep the 10-minute grace rule and count late minutes from shift start. |
| 10 | `compute_work_hours()` | Python's built-in `round()` uses ties-to-even behavior, but the contract requires half-up rounding. | Test a duration whose hour value lands on a half-cent boundary and compare the expected half-up result. | Calculate elapsed seconds and use `Decimal` with `ROUND_HALF_UP` to two decimal places. |
| 11 | `compute_overtime()` | The starter uses the same calendar date for shift end, which fails for overnight shifts; it also counts any positive overtime instead of applying the 30-minute minimum. Its naive punch-out datetime can also be subtracted from a timezone-aware shift-end datetime, causing a `TypeError`. | For a `22:00–06:00` shift, punch out at 06:20 should give 0 overtime; punch out at 06:30 should give 30. | Calculate the correct shift-end instant and return overtime only when floored overtime is at least 30 minutes. |
| 12 | `punch_in()` | An unknown employee is not handled before the code accesses the employee's shift fields. | Punch in with a code that does not exist; the starter can raise an internal error instead of returning 404. | Check the employee lookup and return HTTP 404 for an unknown code. |
| 13 | `punch_in()` timestamp handling | `datetime.fromtimestamp()` uses the machine's local timezone, and timestamp `0` is treated as if no timestamp was supplied. The API requires epoch milliseconds and IST attendance dates. | Send a timestamp from another timezone or a seconds-based value; check the stored date and response. | Validate epoch-millisecond integers, convert to UTC, derive attendance dates in IST, and use current time only when the field is omitted. |
| 14 | `punch_in()` status and duplicate handling | The starter accepts arbitrary status strings and checks for an existing record before inserting, which is not safe under concurrent requests. | Send `status="HOLIDAY"` or simultaneous punch-in requests for the same employee/date. | Restrict statuses to `PRESENT`, `WFH`, and `ON_DUTY`; use the unique employee/date index and return 409 for duplicates. |
| 15 | `punch_in()` response and stored timestamps | The starter returns an `id` for an attendance record, and timestamps may be stored as naive machine-local values instead of UTC. | Inspect the response and stored BSON dates after a punch-in. | Store timestamps as UTC datetimes, truncate to whole seconds, and omit `_id`/extra `id` fields from public responses. |
| 16 | `list_attendance()` validation | Date strings and status values are not validated, and invalid page values can produce unexpected slices. | Try an impossible date, a reversed date range, an unknown status, or `page=0`. | Validate date formats and ordering, restrict status to documented values, and enforce pagination limits. |
| 17 | `list_attendance()` query and pagination | It loads all matching records into Python, sorts them in memory, and only then paginates. This wastes memory and work on a large dataset. | Query a large collection and inspect latency/memory; all matching documents are fetched even for page 1. | Apply sorting, skip, and limit in MongoDB, and use `count_documents()` with the same filters for `total`. |
| 18 | `list_attendance()` response | Raw MongoDB documents can include `_id` and BSON datetime objects, which do not match the API response contract. | Inspect the JSON response for `_id`, an extra `id`, or timestamp fields that are not epoch milliseconds. | Serialize datetimes as epoch milliseconds and omit `_id` from public records. |
| 19 | Required routes missing from the starter | The starter leaves punch-out, regularization, monthly analytics, department summary, late leaderboard, department trend, and explain endpoints as TODOs. | Open `/openapi.json` or call each documented route; the starter does not implement them. | Implement the documented endpoints, including validation and response fields. |
| 20 | `punch_out()` (missing from starter) | Without punch-out, the API cannot close an attendance record or calculate work hours, half-day status, and overtime. | Punch in and then call `POST /attendance/punch-out`; the starter has no route. | Find the latest applicable open record, validate elapsed time, calculate derived fields, and update the record atomically. |
| 21 | `regularize()` (missing from starter) | The starter cannot correct attendance or maintain the required manual-correction audit trail. | PATCH an existing record; the route is missing. | Validate changes, recompute derived fields, reject no-op/invalid changes, and append a history entry with actor, reason, time, and changed values. |
| 22 | Monthly and department analytics (missing from starter) | The starter cannot provide required attendance counts, department metrics, leaderboard, or daily trend. | Call the documented `/analytics/...` routes; they are missing. | Implement the analytics with MongoDB aggregation and apply weekday, headcount, half-day, and rounding rules. |
| 23 | `/admin/explain/{endpoint}` (missing from starter) | There is no way to inspect query plans as required by the assignment. | Call the documented explain route; it is missing. | Add an explain endpoint for supported query types and return the execution plan as JSON-safe data. |

## Reviewed but not considered defects

- **Ten-minute grace period:** A punch-in exactly 10 minutes after shift start is not late. Once the delay is greater than 10 minutes, `late_minutes` is counted from shift start, not from the end of the grace period. This matches the rule.
- **No holiday calendar:** Working days are Monday through Friday only. Not excluding public holidays is intentional because the assignment specifies no holiday calendar.
- **Missing record versus `ABSENT`:** A weekday with no attendance document is not automatically an absent day. The data model explicitly distinguishes these cases.
- **Presence statuses:** `PRESENT`, `WFH`, and `ON_DUTY` count as present; `ABSENT` and `LEAVE` do not. This is the specified behavior.
- **Weekend records:** Weekend attendance records do not add to monthly `present_days`, but they can still contribute to late and overtime totals. This is intentional.
- **Half-day counting:** A half day contributes 0.5 to present-day totals, and the stored `half_day` flag is calculated after work hours have been rounded. This follows the contract.
- **Correction history:** Only manual regularization should append to `history`; ordinary punch-in and punch-out actions should not. This is intentional.
- **Tied leaderboard ranks:** Employees with equal total late minutes can have the same rank. This is expected for competition ranking.
- **Default page size:** A default of 20 and a maximum of 100 are valid; the defects were the incorrect skip calculation and missing validation in the starter.
